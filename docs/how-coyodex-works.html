coyodex

How coyodex works

coyodex turns a codebase into a map you can read top-down: what the system does, who uses it, which parts do the work, and where each of those claims lives in the code. This page explains the tool from the outside in — the goal first, then the idea behind it, then the steps it runs and what each step leaves behind.

1What the tool does

The problem, and the shape of the answer.

When a coding agent writes a lot of code for you, you end up owning code you never read. It works until the day you need to change it or judge it, and then you have nothing to stand on. coyodex exists to give you that ground back.

You point it at a repository. It reads the project's own documents and its code, and produces a map: a set of connected descriptions, written in plain language, where every single statement is attached to a real file and line number. The map is saved next to your code, committed with it, and opened in a browser as an interactive picture you can click into — from "what this product does" all the way down to the exact line that does it.

Three things make it different from asking an agent to "draw me a diagram of this repo":

It is anchored

Every box, arrow and sentence carries a file and line number. You click a claim and land on the code that backs it.

It is explained

Every element carries a plain-language description of what it is for — not just a name lifted from a folder.

It is challenged

The map is measured, cross-checked against itself, and then re-read by fresh agents whose only job is to prove it wrong.

2The principle it works on

One idea, four consequences.

The idea is this: a description of software is only useful if it can be checked. Prose about a codebase rots silently — nobody can tell a correct paragraph from a confident wrong one. So coyodex refuses to produce prose. It produces a structured record where every claim is small, typed, and points at evidence, which makes the record checkable by a program, by another agent, and by you.

Four consequences follow from that one idea, and they explain nearly every design choice in the tool.

a. The map is data; everything you see is generated

There is exactly one stored map file. The readable text version and the interactive picture are both produced from it on demand and are never edited by hand. So the diagram cannot drift from the description, and the description cannot drift from the record. If you want the map changed, the record changes and the views follow.

b. Every claim carries its evidence

A relationship such as "the sign-up page sends the form to the accounts service" is stored with the line in the page's own code where that call happens. Same for the definition of every part, every outside service, every stored thing, every security check, every step in every story. A claim with no location is treated as an unfinished claim, not as a small omission — the tooling blocks on it.

c. The map is written twice, on purpose, so the two copies can argue

coyodex records the system on two sides that are built from different sources and must agree.

d. Nothing is trusted because a smart agent wrote it

The map is produced by an agent, so the method assumes the agent is wrong in predictable ways and builds the answer around that assumption: measure the code with programs instead of guessing sizes, check the record with programs instead of re-reading it, and hand the finished claims to different agents that never saw the reasoning and are asked to disprove them. That is covered in section 6.

3The hard parts, and how each is handled

Five real problems in mapping a codebase, and the specific answer to each.

The challengeWhy it defeats the naive approachWhat coyodex does
The codebase does not fit in one head One agent reading a whole repo runs out of room and starts summarising instead of reading, so whole areas quietly become one vague box. The work is split into slices with no overlap and given to many agents at once, each returning a small structured result instead of text. A separate step merges them and settles the naming.
An agent describing code invents things Plausible-sounding architecture is easy to produce and impossible to spot later. Typical inventions: crediting a part with an outside call that a helper it uses actually makes, or calling a part the owner of data it only passes along. Every claim must carry the line that proves it. Programs then check those lines exist and actually do something. Finally fresh agents re-read the code and try to refute each claim, and a refutation is itself re-checked before the map is edited.
Choosing the right level of detail Too coarse and a heavy area collapses into one meaningless box; too fine and you get 400 boxes nobody can read. Judged by eye, this drifts wildly between runs. The code is measured first — size, file counts, change history per folder — and that measurement produces an expected number of parts, with a generous tolerance band. The agent still decides; the number tells it where to look and forces it to write down a reason when it disagrees.
Diagrams that are technically right but unreadable A correct picture with 40 boxes on one screen teaches nobody anything. A readability rule sizes the screens: each level shows about five to seven boxes, and deeper levels are created until that holds. A checking program reports every screen outside the band.
The map goes stale the day after it is written A document that describes last month's code is worse than none, because people still trust it. The map records exactly which commit it describes, and is committed together with the code. So there is never any doubt about which version of the code a map is talking about, or how far the code has moved since — unlike a document with no date on it, which people keep trusting long after it stopped being true.
The failure this is really guarding against

A map that has never been challenged and a map that has been fully verified look identical, read identically, and pass every automatic check identically. That is why the verification pass is compulsory, why it is done by agents that did not build the map, and why the map itself stores the count of how many claims were challenged and how many survived. An unchallenged map says so.

4What is actually in a map

The contents, and how you move through them.

A map is one record holding the following, all cross-linked. You never read it as a file — you read it through the browser view, one level at a time.

The story

The goal in a paragraph. The project's vocabulary. Who starts things and what they want. The jobs the system does. One end-to-end walk-through of those jobs.

The structure

Parts of the code grouped into nested levels, each with a purpose, the technology it is written in, and where it lives.

The ways in

Every route, command, tool, webhook — and, separately, everything that starts by itself: scheduled jobs, background loops, queue readers, startup hooks, with how often each runs.

The things it knows about

The real named data types with their fields and the relations between them, grouped into areas when there are many, plus where each one is stored.

The links

One project-wide list of who calls, reads, writes, routes to, enforces or persists what — each with a short reason and a code line.

The step-by-step stories

One ordered flow per job. Machinery shared by several stories is written once and referenced, so it is told the same way everywhere.

The running system

Which processes exist, what runs inside each one, which ones talk to which, and which environments each one is deployed in.

The operational facts

How to run and build it, what it logs and where, what the access-control surfaces are and where each check is enforced, what the settings are.

The test gaps

Not a coverage percentage — a list of the things that matter, each marked tested or not, with the risk of the gap.

The honesty record

Confidence on every element (checked against code, or inferred), how many claims were challenged and how many held up, and any warning the team decided to accept, with the reason written into the map.

The browser view presents these as separate tabs, ordered from what the system does towards how it runs: the walk-through, the jobs by user, the structure, the data types, the outside dependencies, the storage, the processes, the operational tables, the vocabulary, and the test gaps. Each tab states in one line the question it answers.

5How a map gets built

The build, step by step, and what each step leaves behind.

You type one command and the agent runs the sequence below. Some steps are done by a single agent working alone; some fan out to many agents working at the same time; some are checking programs. The order is not cosmetic — each step needs the previous one's output, and the two "everyone stops here" points exist to prevent specific mistakes.

one agent many agents at once a checking program

0
Decide what is being asked one agent

Before anything else the tool looks for an existing map. No map means build a new one. A map that exists is left alone — a rebuild throws away a reviewed, corrected map, so it only happens if you ask for it in so many words.

1
Read what the project says about itself one agent

The README, the docs folder, the contributing guide, the package descriptions. These are the only source for the parts the code cannot tell you: what the product is for, who it is for, and which features matter most. They are treated as intentions, not facts — anything taken from them stays marked as inferred until the code confirms it, and where docs and code disagree, the code wins.

Leaves behind: the story side in draft — goal, vocabulary, the people involved, the jobs, a first ordering of the walk-through.
2
Measure the code a checking program

A program walks the whole tree and reports, per folder: how much code, how many files, how often it changes in git, plus an index of where every class and function is defined. From that it computes how many parts a map of this repo should have, roughly, and where the heavy areas are. It also reports what it could not read, so unparsed areas are treated as unknown rather than empty.

This deliberately runs after the story draft, so that the numbers set where to look and the human story still sets the names.

Leaves behind: a measurement file, committed with the map — the browser view also uses it to search for symbols.
3
Collect the pieces many agents at once

The repo is cut into slices with no overlap, sized from the measurement so no slice becomes the one everybody waits for, and all the agents are launched together in a single instruction. Each one reads its slice and returns structured rows, never file dumps: the parts and their purposes, the ways in, the outside services, the data types with their fields and relations, the build and run commands.

Two rules here come from real failures. Every agent writes its work to a draft file as it goes, so an agent that dies does not lose an hour of reading. And exactly one agent owns the data-type pass for the whole repo — split that up and the relations between data types come out thin.

There is also a required second sweep for everything that starts by itself: scheduled jobs, background loops, queue readers, startup hooks. These have no caller, so a search that follows callers never finds them, and a long-running service that reports none of them is treated as a red flag.

Leaves behind: one structured file per slice.
4
Merge — everyone stops here one agent

One agent merges the slices: removes duplicates, settles the final names and identifiers, groups the parts into levels, groups the data types into areas, and links each part to the process it runs in by reading the deployment files.

This is a hard stop for one reason only: identifiers must be final before anything references them, or later work points at names that no longer exist. Everything else here is written as a declarative assignment file, so re-merging the pieces always reproduces the same result — a map that cannot be rebuilt from its inputs has quietly stopped being generated.

It is also the moment the drafted jobs are checked against reality in both directions: a job the docs describe with no way into the system behind it, and a real public entry point that no job claims. Both happen, and both are fixed here rather than traced wrongly afterwards.

Leaves behind: the first complete map — all the parts, none of the links.
5
Follow the stories through the code many agents at once

One agent per job (or per area, on a big repo). Each traces its job from the way in to the outcome and writes the ordered steps: which part hands to which part, what happens at that point in one present-tense phrase, and the exact line where that step fires. Steps may go backwards too — the response the user sees, an error path, a callback — because those carry meaning.

The same agents record the links for their slice: who calls, reads, writes, enforces what, each with its reason and a witnessing line. Machinery that appears in two or more stories is pulled out and written once, so it is told at the same depth everywhere.

Leaves behind: every story, and the project-wide list of links.
6
Re-check the grouping, now that the links exist one agent a checking program

The grouping in step 4 was decided before any link had been traced, so it was made half-blind. A program now reports the fan-out of every screen, the traffic between groups, and where a split would help. Each finding is either fixed or given a written reason that is stored in the map — so the same warning does not re-appear forever with nobody remembering why it was accepted.

7
Compare against the tests one agent

Walk the finished inventory — jobs, ways in, data types, risky branches — and for each ask whether a test exercises it. The output is a risk-ranked list of gaps, not a percentage. Reading the tests gives an inferred answer; only running them with coverage makes it measured, and the map states which of the two happened.

Leaves behind: the test-gap table.
8
Try to disprove it many agents at once

The checking program produces a worklist of every claim that no program can settle — "this part really does call that service", "this part really is the owner of that data", "this check really enforces access here" — ranked most dangerous first. The claims are grouped by theme and handed to fresh agents that have never seen the build reasoning, one batch each, each asked to refute its claims against the code.

Three verdicts are allowed and all three are real: confirmed, refuted, or cannot be settled either way. For the most dangerous claims, an odd number of at least three agents vote. Every refutation is then re-checked against the code before the map is edited, because a wrong refutation corrupts the map just as silently as the error it claims to fix.

Leaves behind: the corrected map, plus a stored record: how many claims existed, how many were challenged, how many were confirmed, refuted, or unsettled.
9
The gates, then publish a checking program

One command runs all the checks and writes the findings to a report file — deliberately a file, because a summary written from memory has been wrong before. It also states whether every check actually ran, since a check that was skipped otherwise looks exactly like a check that passed.

Then the map is stamped with the commit it describes and committed together with your code.

Leaves behind: the committed map, its readable version, the measurement file, and the gate report.

6The quality gates

Three layers of checking, each catching what the one before it cannot.

Two habits that make the checking real

  • A warning is answered, never hidden. Each accepted warning is written into the map with its reason, under a heading the checking program reads — so it stops firing, and the reason survives for the next person. Filtering a warning out of your own view is not an answer, and the tool reports how many warnings a written reason silenced so a quiet check is never mistaken for a clean one.
  • Confidence is stated per element. Structure read from source is marked checked; intent taken from documents is marked inferred. The distinction is visible in the view, so you know which parts of the map to trust and which to sanity-check.

7What you get, on disk

Three files and a local server.

ArtefactCommitted?What it is for
.coyodex/project-map.jsonyesThe map itself — the only source. Written by the tooling, never by hand. Records the commit it describes.
.coyodex/project-map.mdyesA readable text rendering of the same map, so a change to the map shows up as a reviewable diff in a pull request.
.coyodex/preindex.jsonyesThe code measurement taken at that commit; the browser view uses it to find symbols.
The interactive viewnot a fileServed on demand from the map by a small local server, so the picture can never be out of step with the record. It reads your source from git at the map's commit, so what you see matches the map even if your working copy has moved on.
.coyodex/.ignoreoptionalCode that is committed but is not part of what the map should describe — a vendored copy, a fixture tree, generated output. Everything that measures the repo respects it, and the tool always reports how many files it removed, because excluding too much would make the map look more complete than it is.

8Shaping the map after it is built

The first map is a starting point, not a verdict.

A built map is rarely right in every judgement the first time: a grouping reads oddly, a name is the code's name rather than the product's, one area deserves more detail than the rest. You do not have to rebuild to fix that, and you do not have to edit the stored file by hand. You ask, in plain language, and the tool rewrites the map and re-runs the same checks it runs on any other write.

Two things you can ask for:

  • Reorganise or rename — "move the payments module into a new billing group", "split this part in two", "rename this group". The tool edits the map directly and runs the same gates as any other write. It will reorganise and rename what exists, but it will not add something the code does not back.
  • Go deeper in one area — when a part turns out to be a whole area, it becomes a group and its real units become the parts under it, with its links re-traced to the specific new parts. Detail can be uneven: you refine only where you need it, and everything else stays one box. This always happens inside the one map — there is never a second map file, because a second file means a second set of names that nothing can link across.

9The commands you will actually type

Everything above is driven from these.

CommandWhat happens
/coyodexBuilds a map, running the whole sequence in section 5. It never silently rebuilds over a map that is already there.
/coyodex <request>Any plain-language request about the map itself — move, split, rename, or go deeper in one area (section 8).
make startStarts the local server once. Every project you map appears there as a card; leave it running.
Worth knowing before you rely on it

coyodex is early and experimental. The stored format still changes, so treat maps as replaceable; it has been exercised mainly on small and medium repositories; and the quality of a map depends on the coding agent that built it — expect to read it and correct it. The verification pass exists precisely because that is true, not as a substitute for your own eyes.
